# Autopilot Campaign

<!-- arlotope:contract (generated by `arlotope docs` from workflow/) -->
**First, load the brief:** `uv run --with pyyaml python arlotope.py brief autopilot [--study <slug>]` — skip it if a `ARLOTOPE BRIEF /autopilot` block is already in your context. It says where the study stands, the PI's own instructions for this work, and the checkpoints.

**Show the PI** (`python tools/artifact.py publish --title "…" --file <path>`): a short report per campaign pass: what moved, what is waiting on the PI, what the next pass will do. One artifact for what they would genuinely want to see — not a running commentary. A decision you need takes `--question "…" --choices "A;B"` (the answer comes back to this run); it is never an approval.

**Read first:** `AGENT-GUIDE.md` — "Programmatic agents", "Headless runs under the executor" (it binds exactly like AGENTS.md).
<!-- /arlotope:contract -->

The full-autonomy mode: "one approval before bed, papers in the morning." The campaign carries each
study along its workflow until it waits for the PI, is shelved, or has finished (for the research
workflow: a fully drafted, claims-audited, ensemble-reviewed paper waiting for the PI's go to finalize
it). Only if the PI delegated a checkpoint to the campaign does the executor's campaign keeper approve
it, after running its checks itself (never an agent; see "Under the campaign keeper" below). Nothing is
ever sent outside the lab.

**Started from the dashboard** (the usual way): the PI approves the brief in the campaign form (the
record `campaign:<name>`), choosing which checkpoints it may approve, and the executor's **campaign
keeper** carries it — it starts each `/autopilot continue` cycle, restarts after timeouts, usage limits
and transient failures, runs the procedures you dispatch, and stops at the deadline or budget. Follow
**"Under the campaign keeper"** below. The authorization conversation (§1) and the executor path in §2
are for campaigns started by hand in a session.

## 1. Authorization conversation (10 minutes, the only interactive part)

1. Ask the PI: direction(s); how many ideas to carry; total compute/wall-clock budget; which of
   the workflow's checkpoints the campaign may approve (only those whose `approver` is
   `me-or-campaign`), and the bounds it approves them within. **Project concurrency** is
   `autopilot.max_concurrent_projects` (default **1** — one project carried end-to-end before the
   next). >1 means concurrent multi-project, which **requires** `agents.programmatic.enabled: true`
   (see §2's concurrent path); confirm both with the PI and record the chosen value + whether
   programmatic launching is exercised in the brief, so the approval covers it.
2. Fill `templates/loop/CAMPAIGN.md` → `lab/campaigns/<date>-<slug>.md` and present it. The
   brief's "Checkpoints this campaign may approve" section lists the delegated checkpoints; every
   other checkpoint waits for the PI. A delegated checkpoint is approved only by the keeper, on a
   cycle's request, after it re-checks the bounds and runs the checkpoint's checks. The agent never
   widens a bound or claims an approval beyond what the brief covers.
3. The PI approves the brief (the dashboard's campaign form, which records `campaign:<name>`) →
   begin. No approved brief, no campaign.

## 2. The campaign loop (unattended)

**Default — one project end-to-end at a time** (`autopilot.max_concurrent_projects: 1`): carry one
idea fully through the loop below (or to a kill) **before** starting the next. This keeps a single
project's frozen set / budget / ledgers in working memory — aligned with `compute.max_concurrent_runs: 1`
(training is serial regardless). Within that project you still interleave *its own* CPU-light work
around *its* in-flight training (zero-token monitoring, the compute-share rule).

**Concurrent multi-project** (`autopilot.max_concurrent_projects > 1` **and**
`agents.programmatic.enabled: true`): do **not** cram many projects into this one context, and do
**not** hand-background per-project shell commands. The usual way is a campaign started from the
dashboard (its keeper dispatches each project's procedures; see "Under the campaign keeper" below).
From a session, this session becomes a **coordinator** and hands each project to the executor as its
own run:

```bash
uv run --with pyyaml python tools/executor_cli.py enqueue --target <slug> --prompt-file <brief>   # one per project; {{slug}} is substituted
uv run --with pyyaml python tools/executor_cli.py list                                            # what is queued / running / waiting
uv run --with pyyaml python tools/executor_cli.py stop --target <slug>                            # stop one project's runs
```

The executor caps concurrency itself (`agents.programmatic.max_concurrent*`), runs each project as a
headless top-level session in its own repo (a detached supervisor with a durable record), and every
run is traced and visible in the dashboard. Training still follows the compute-share rule (hard
rule 13: at most `compute.max_concurrent_runs` training campaigns at once; the Compute panel shows
what is running); CPU-light work runs in parallel across sessions. The coordinator's job is narrow:
enqueue, then monitor each project's Campaign Log / `arlotope.py status` / `.bus` for completion or
escalation, and write the unified morning report. Each launched session is **top-level** (it writes
its OWN project ledgers), runs exactly the per-idea loop below, and **stops at every checkpoint
that is not approved** (`needs_pi=<checkpoint id>`); the launch depth is capped so a launched agent
can't launch more. **State the brakes in the prompt-file** — "stop at every unapproved checkpoint
and report `needs_pi`; **never `/finalize`**; escalate via `lab_bus.py` rather than widening
anything". Programmatic launching is **PI-owned and OFF by default**; see `docs/autonomy.md`.

The per-idea loop (run by this session, or by each launched session):

```
per idea:  repeat
             uv run --with pyyaml python arlotope.py next <slug>   → the procedure to run
             run that procedure for the study                   → it reports its outcome (arlotope move)
           until `next` says the study waits for the PI, is shelved, or has finished
           when it waits at a checkpoint:
               delegated to the campaign → check the evidence against the brief's bounds
                                           (oversight.level ≠ off: an overseer `support` check
                                            confirms "within bounds" first), then ask the keeper:
                                           within bounds → the keeper approves it and starts what follows
                                           outside       → it waits for the PI; take the next idea
               not delegated             → it waits for the PI; take the next idea
```

Campaign rules (in addition to every standing hard rule):
- **All ordinary machinery applies unchanged** — checkpoints, budgets, ledgers, oversight checks,
  author-response triage, claims audits. A campaign is normal operation minus the wait for the PI,
  never a relaxed mode.
- Kill criteria fire exactly as in interactive mode; a night that kills 3 ideas cheaply and ships
  1 strong draft beats 4 weak drafts. On each idea's kill or completion, run
  `uv run --with pyyaml python tools/guard.py evolve <slug>` — a BLOCK means the kill left no
  CORRECTION (or a results-stage exit no RECIPE); write the FAILURES/FINDINGS + NOTES entry before
  taking the next idea.
- NEEDS-EXPERIMENT review items are followed within remaining budget; otherwise queued.
- **Explore-mode pivots** (if the campaign authorized `explore`): a project loop may reopen
  `Headline: no` decisions and expand the frontier autonomously within its budget — the routing
  rule is `/improve`'s `revisit`/`expand`, don't re-derive it here. A `Headline: yes` reopen routes
  to **`/ideate --in-project <slug>`** (or, if `ideation.in_project: false`, a successor hub
  `/ideate`). **Campaign delta:** under `ideation.in_project_approval: campaign_auto` a surviving
  approach is checked against the campaign's bounds + an overseer `support` pass — **exactly like a
  request to approve a delegated checkpoint** — then routes through `/propose` → re-plan; outside
  bounds (or `in_project_approval: pi`) it queues for the PI. Emit `approach_ideate` (per round) and
  `replan` (when an approach re-plans the project, mid-campaign — not only at exit). Frozen-set
  changes and budget overruns are never delegated; a checkpoint is approved only by the PI or, if
  delegated, by the keeper.
- Every procedure run appends a Campaign Log row **and** emits a bus event
  (`tools/lab_bus.py emit cycle --idea <slug> --detail "<procedure> → <outcome>"`); at the start of each
  portfolio pass, check `tools/lab_bus.py inbox` and act on any PI directive.

## 3. Morning report (campaign exit)

Write at the top of the notebook entry, in this order:
1. **Studies waiting at a checkpoint** — per study: the checkpoint, and for a paper: title,
   headline result (with run ids), ensemble median Overall, unresolved review items.
2. **Killed/parked ideas** with one-line reasons (knowledge, not failure).
3. **Queued PI decisions** — work outside the delegated bounds, frozen-setting requests.
4. Budget actually spent vs the brief; recommended next command.
Then the standard write-back (notebook, knowledge promotion) for everything touched.

## Re-entry — `/autopilot continue <campaign-file>`

Invoked with `continue <campaign-file>` (the form `/loop` fires), this is a **resume**,
not a fresh start — **skip §1 entirely** (never interview an absent PI at 3am):

1. Read the named brief. If the PI has not approved it (`uv run --with pyyaml python arlotope.py
   approved lab campaign:<name>` exits 1), STOP with a note — never approve it yourself.
2. Rebuild state from written record: the Campaign Log tail + `arlotope.py status` + each
   spawned project's `runs/registry.jsonl` and `EXPERIMENT_LOG.md`.
3. **Reconcile the crashed session before launching anything:** run `scripts/status.py` in each
   active project (in-flight run → re-attach monitoring instead of launching new work; dead run →
   record it failed). **If the campaign launched headless runs** (`agents.programmatic.enabled`),
   also run `uv run --with pyyaml python tools/executor_cli.py reconcile` — it marks any run whose supervisor died as failed and emits
   `agent_finished`, so you don't relaunch over a phantom (`uv run --with pyyaml python tools/executor_cli.py list` shows what's still alive). Treat the
   last Campaign Log row as possibly half-done: confirm its artifacts exist before re-running the
   procedure.
4. **If a stop condition already holds** (wall-clock expired, environment failure logged, every
   idea waiting, shelved or finished), go straight to §3 and write the morning report — an empty or
   crashed night still gets a report with budget-spent and a one-line diagnosis. Otherwise resume §2
   with `arlotope.py next` for each idea.

Campaign Log rows are appended **on each procedure's completion, before starting the next** —
so the row after the last one is the resume point, and a missing row means re-verify.

## Under the campaign keeper (a dashboard-started campaign)

The run's preamble says `CAMPAIGN CYCLE n of <campaign>`. Then:

1. **One cycle = one portfolio pass**, the Re-entry path above (never §1): rebuild state, reconcile,
   and take each idea's next procedure from `arlotope.py next <slug>`.
2. **Dispatch, don't do.** Start each procedure as its own run:
   `python tools/lab_bus.py emit campaign_dispatch --run-id $ARLOTOPE_RUN_ID --data skill=<procedure> --data target=<slug or hub>`
   (optional `--data args="<args>"`). Dispatch only the work of the step a study is at (its procedure,
   or one the step offers). The keeper validates it (a launchable procedure, the study belongs to this
   campaign and isn't waiting for the PI, no duplicate, the brief's parallelism) and runs it with
   retries; the procedure reports its own outcome, and the result is in the study's files and the run's
   footer by your next cycle. Short CPU-light bookkeeping (the Campaign Log, the notebook) you may do
   yourself.
3. **Membership:** append the idea's Campaign Log row **before** dispatching its first procedure — the
   log is how the keeper knows the study is part of this campaign.
4. **The PI is away.** Ask only what you can't decide within the brief: ONE question, concrete options,
   your recommendation first — if nobody answers in time the recommendation is taken and shown to the PI
   as assumed. A decision outside the brief (a proposal out of bounds, a kill decision, a frozen-set
   change) is never assumed: that study's own run reports it (an outcome the PI decides, or `needs_pi`
   with `study=<slug>`) and only that study waits; carry on with the others. Read PI directives
   (`tools/lab_bus.py inbox`) and the answers in your preamble each pass.
5. **Checkpoints:** never dispatch for a study that waits. A study waiting at a checkpoint the brief
   delegates to this campaign (one its outcome would pass, or one its run stopped at with
   `needs_pi=<id>`): when its evidence meets the brief's bounds (have the overseer check it first), ask
   the keeper with `python tools/lab_bus.py emit campaign_approve --run-id $ARLOTOPE_RUN_ID --data
   study=<slug> --data checkpoint=<id> --data why="<≤200 chars>"`. The keeper re-checks everything (the
   campaign is still approved, the checkpoint is delegated, the study is a member and not held, no
   escalation is open), runs the checkpoint's checks, and records the approval as this campaign's. When
   that moves the study on, the keeper starts the new step's procedure itself — don't dispatch it again.
   Any other checkpoint waits for the PI.
6. **Footer:** end every cycle with the run footer plus `--data campaign=continue|idle|done` (`done` when
   every target study is finished, shelved or waiting on the PI, or a stop condition holds). A cycle
   marked FINAL (deadline, budget, or the PI's Stop) dispatches nothing and writes the morning report (§3).

The keeper is the scheduler: don't `/loop`, don't background yourself, don't enqueue runs yourself.

## Keeping it running (a campaign started by hand in a session)

Within one session this skill just runs. For resilience across a long night, pair it with Claude
Code's built-in scheduler: `/loop 30m /autopilot continue <campaign-file>` re-enters the campaign
on an interval (the Re-entry path above). The brief + append-only logs make every procedure run
recoverable. The session must stay open with a permission mode that won't prompt mid-night — see
docs/autonomy.md for the exact invocation and its limits.
