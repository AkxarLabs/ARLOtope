# Literature Review

<!-- arlotope:contract (generated by `arlotope docs` from workflow/) -->
**First, load the brief:** `uv run --with pyyaml python arlotope.py brief lit-review --study <slug>` — skip it if a `ARLOTOPE BRIEF /lit-review` block is already in your context. It says where the study stands, the PI's own instructions for this work, and the checkpoints.

**Finish by reporting one outcome** — `done`, `incremental`, `inconclusive`, `park`, `kill` — with `uv run --with pyyaml python arlotope.py move <slug> <outcome> --note "…"`. The study's workflow decides where it goes (the brief lists each outcome's destination); never edit lab/REGISTRY.md or lab/journal.jsonl.

**It must produce:**
- studies/<slug>/lit-review.md: search log, per-paper notes, novelty verdict (novel|incremental|done-before|inconclusive), positioning

**Show the PI** (`python tools/artifact.py publish --title "…" --file <path>`): the novelty verdict with the 3–5 closest papers and how this idea differs — a short Markdown note, once lit-review.md is written. One artifact for what they would genuinely want to see — not a running commentary. A decision you need takes `--question "…" --choices "A;B"` (the answer comes back to this run); it is never an approval.
<!-- /arlotope:contract -->

Output: `studies/<slug>/lit-review.md` (from `templates/idea/lit-review.md`) and a novelty verdict.

Retain useful papers as source records with the knowledge command in the run brief:
`add --kind source --title "..." --url "..." --coverage abstract --text "..."`.
Include DOI/version when known. Record only what was actually read; do not automatically capture
every search hit. Keep the literature review and REFERENCES index as well.

## Procedure

1. Read `studies/<slug>/IDEA.md`, including its triage notes if it has them.
2. **Search.**
   - Start from the hypothesis's key terms, then widen: synonyms, the methods the first good hits cite,
     and the "cited by" chains of the closest works.
   - Use `.claude/skills/lit-review/tools/s2.py search "<query>" [--year 2022:]` for replayable, logged
     Semantic Scholar queries (OpenAlex fallback built in). Combine it with web search and fetch for
     arXiv and Scholar coverage.
   - Log EVERY query in the search log table.
   - **Loop until dry:** stop when two consecutive searches surface nothing new and relevant (typically
     8–15 queries).
   - The live search stops at `litreview.max_minutes` (`lab/config.yaml`; 0 = unbounded) even if it is
     not dry. If the cap stops you, **log what was NOT covered** in the search log.
   - **A query that errors or exits 3 (both backends unreachable — see s2.py) does not count** toward the
     "nothing new" rule. An empty result from it is not evidence of absence.
   - If the APIs are down and web search can't compensate, record the review as *blocked* in the search
     log. Never give a `novel` verdict from an empty or failed search.
3. **Read and note** the relevant papers (typically 5–15).
   - Fetch the actual abstract or paper and record what it *actually shows* (scale, conditions, numbers),
     not what its title implies. These notes are the only permitted citation source later.
   - Pick the 1–3 load-bearing papers the verdict hinges on and run `/critique-paper <link>` (external
     mode) on each; store the output under `studies/<slug>/critiques/`. A "SOTA" that doesn't survive
     critique changes the baseline obligations.
   - The deep notes stay in `lit-review.md`. Also add a **one-line pointer** for each keeper to
     `lab/knowledge/REFERENCES.md` (`| bibkey | Authors, "Title", venue year — link | one-line
     what-it-shows | <slug> |`). For a bibkey already in the index, add this `<slug>` to its `seen-for`
     instead.
4. **Novelty verdict.** Be adversarial: assume someone has done this. Record the closest prior work and
   the precise delta, then one of `novel`, `incremental` (say what the increment is and whether it is cheap
   and useful), `done-before`, or `inconclusive`.
5. **Positioning** (the proposal's baselines and risks are built from it): the baselines the field will
   demand, the expected metrics and benchmarks, and the pitfalls the closest works report.
6. **Report the outcome** (`arlotope.py move <slug> <outcome> --note "…"`):
   - `novel` → `done`.
   - `incremental` → `incremental`, or `done` if the PI's instructions in the brief already settle it.
   - `inconclusive` (including a blocked search) → `inconclusive`.
   - `done-before` → `kill`, or `park` if a variant is worth a later look. Record the reason in IDEA.md
     and harvest any surviving variant into `lab/knowledge/OPEN-QUESTIONS.md` (`FAILURES.md` is for
     things *tried* that failed, not ideas stopped before any experiment).

   The note gives the verdict, the closest work and the delta in one line. If `arlotope move` says the study
   waits for the PI, present the verdict with the 3 most load-bearing papers and stop (headless:
   `needs_pi=<the outcome>`).
