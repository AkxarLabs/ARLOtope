# Experiment Loop

<!-- arlotope:contract (generated by `arlo docs` from workflow/) -->
**First, load the brief:** `<hub>/arlo.py brief experiment --study <slug>` (`<hub>` = this project's `control.yaml` `hub_path`); skip when `ARLOTOPE BRIEF /experiment` is already supplied. It states how to finish, what to produce and show the PI, and the PI's additions and checkpoints.
**Read first:** `<hub>/AGENT-GUIDE.md` — "Mechanical guards (tools/guard.py)".
<!-- /arlotope:contract -->

Operates inside the project repo at `<projects_root>/<slug>`. The project's `control.yaml` carries its run controls (budgets, seeds, parallelism). What a *run*, a *stage*, and *multi-seed* concretely mean is set by the project's **`TYPE.md`** (default `ml`; e.g. for `empirical`, "multi-seed" = bootstrap and a "run" is a `runner: shell-command` spec via `scripts/run.py`).

This procedure can also run at a step whose own procedure is another one. Report an outcome only if the brief's "When your work on this step is done" section lists outcomes for you; if it says you run alongside the step's own procedure, do the work and just finish.

## Before each experiment: read memory

**Check the inbox** (AGENTS.md's per-attempt checkpoint): `uv run --with pyyaml python scripts/lab_bus.py inbox` — a PI directive may request/steer/stop the next run; act within the protocol and ack (a directive that would touch a frozen/PI-owned setting is acked `blocked`). Then read `PLAN.md` (what's next + its criterion), `NOTES.md` **in full once per session** (distilled gotchas + approaches tried-and-abandoned; its headings after that), `SYSTEM.md` if present (PI machine constraints — binding like control.yaml, never edited), and `scripts/compare.py digest` (the last ledger entries with their parents, the kill criteria, the NOTES headings) instead of the raw ledger, registry and `git log`; open those only for a specific entry. Never re-run something already tried, or a known dead end, without saying why.

## Per experiment attempt

1. **Config first.** New YAML in `configs/experiments/` (immutable once run; variants = new files). New behaviour goes behind a config switch; the baseline path stays untouched.
2. **Stage discipline:**
   - **SMOKE** — minutes; required for any new code path. It proves the pipeline and the artifacts end to end, and nothing more.
   - **PILOT** — the smallest run that can meet, or fail, the row's pre-written criterion. A pilot that can't possibly fail is too small or measures the wrong thing.
   - **FULL** — only after a pilot justified it. State the budget, the expected wall-clock, and the decision the run informs. If the brief lists a `during` checkpoint whose `at` covers full-scale runs, check it before launching: `<hub>/arlo.py approved <slug> <checkpoint-id>` — exit 0 = approved (follow the PI's note on it: how many runs, how long); nonzero = present the trial results against their promotion criteria and the planned full runs against the budget, end with `needs_pi=<checkpoint-id>`, and stop. Use the checkpoint's configured decision maker; never approve your own work. Unapproved full runs are flagged. With no such checkpoint, go on. Before any FULL run, also run `<hub>/tools/guard.py frozen <slug>` — confirms `eval_frozen` + the PI-owned blocks are intact.
3. **Run** via `scripts/run.py` (long runs: background with output capture). Before a PILOT/FULL run, follow the compute-share rule (hard rule 13): if the lab already runs `compute.max_concurrent_runs` training campaigns (the dashboard's Compute panel, or `arlo panel compute`), wait or do CPU-light work. Stage budgets come from `control.yaml` (each run's `budget.max_minutes`); they are instructions the Compute panel tracks, not limits a script enforces — stay within them, and a run needing more budget is a PI flag, not a config tweak. On a machine with a job scheduler (the hub's `compute.scheduler`, set in the dashboard → Settings → This machine & compute), `run.py` **submits** PILOT/FULL runs and **waits** for them — same run dir, artifacts and exit codes (the run's `budget.max_minutes` is the job's time limit); the run shows `status=queued` while it waits (never "stalled"). **Never call `sbatch`/`qsub` yourself**, and follow `SYSTEM.md`'s site rules.
4. **Record** in `EXPERIMENT_LOG.md` (template entry format): outcome with run ids, decision (keep/revert/debug/move on), reasoning. Then **one git commit per attempt** — message `exp-NNN: <one-line outcome>`. If the change isn't kept, revert the code but keep the ledger entry and registry line. (`run.py` already emitted the run's bus events; a kill or stage promotion warrants its own `scripts/lab_bus.py emit` event.) After the append + commit, run `<hub>/tools/guard.py append-only <slug>` — confirms the ledger was only appended (never rewritten) and refreshes its baseline.
5. **Update PLAN.md** experiment table (status, result run ids).

## Constraints

The project rules in `AGENTS.md` (debug cap, frozen things, multi-seed, test-once, plan drift, data provenance) bind every attempt. Specific to this procedure:

- **Debugging:** debug from the experiment's *ancestral chain* (its previous attempts), not unrelated history; fix one thing per attempt, and write down the diagnosis even when the fix fails.
- **Data fidelity:** every run's resolved config records the dataset id/hash, row count, split and metric, and they match the frozen plan (`control.yaml` `data:`, `configs/base.yaml` `eval:`). Never subsample, substitute a benchmark or metric, or use synthetic data on your own: stop and ask the PI, and if they agree, record it as a `deviation:` on every affected claim.
- **Kill criteria:** check PLAN.md's kill criteria after every PILOT. If triggered, stop the loop and present the evidence to the PI — recommendation kill/park, their call (headless: run footer `needs_pi=kill_criteria` with the evidence path in `summary`).
