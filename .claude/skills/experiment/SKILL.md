# Experiment Loop

<!-- newts:contract (generated by `newts docs` from workflow/) -->
**First, load the brief:** `uv run --with pyyaml python <hub>/newts.py brief experiment --study <slug>` (`<hub>` = this project's `control.yaml` `hub_path`) — skip it if a `NEWTS BRIEF /experiment` block is already in your context. It says where the study stands, the PI's own instructions for this work, and the checkpoints.

**Finish by reporting one outcome** — `done`, `park`, `kill` — with `uv run --with pyyaml python <hub>/newts.py move <slug> <outcome> --note "…"`. The study's workflow decides where it goes (the brief lists each outcome's destination); never edit lab/REGISTRY.md or lab/journal.jsonl.

**It must produce:**
- configs/experiments/<exp>.yaml per attempt
- EXPERIMENT_LOG.md entry + one commit `exp-NNN: …` per attempt
- PLAN.md experiment table updated
- NOTES.md lessons at exit

**Show the PI** (`python "$NEWTS_HUB/tools/artifact.py" publish --title "…" --file <path>`): a results note when a stage finishes (SMOKE → PILOT, PILOT → FULL): a table of its runs and one figure — never one per attempt. One artifact for what they would genuinely want to see — not a running commentary. A decision you need takes `--question "…" --choices "A;B"` (the answer comes back to this run); it is never an approval.

**Read first:** `<hub>/AGENT-GUIDE.md` — "Mechanical guards (tools/guard.py)" (it binds exactly like AGENTS.md).
<!-- /newts:contract -->

Operates inside the project repo at `<projects_root>/<slug>`. The project's `control.yaml` carries its run controls (budgets, seeds, parallelism). What a *run*, a *stage*, and *multi-seed* concretely mean is set by the project's **`TYPE.md`** (default `ml`; e.g. for `empirical`, "multi-seed" = bootstrap and a "run" is a `runner: shell-command` spec via `scripts/run.py`).

This procedure can also run at a step whose own procedure is another one. Report an outcome only if the brief's "When your work on this step is done" section lists outcomes for you; if it says you run alongside the step's own procedure, do the work and just finish.

## Before each experiment: read memory

**Check the inbox** (AGENTS.md's per-attempt checkpoint): `uv run --with pyyaml python scripts/lab_bus.py inbox` — a PI directive may request/steer/stop the next run; act within the protocol and ack (a directive that would touch a frozen/PI-owned setting is acked `blocked`). Then read `PLAN.md` (what's next + its criterion), `NOTES.md` **in full** (distilled gotchas + approaches tried-and-abandoned), `SYSTEM.md` if present (PI machine constraints — binding like control.yaml, never edited), the tail of `EXPERIMENT_LOG.md`, `runs/registry.jsonl`, and `git log --oneline -20`. Never re-run something already tried, or a known dead end, without saying why.

## Per experiment attempt

1. **Config first.** New YAML in `configs/experiments/` (immutable once run; variants = new files). New behaviour goes behind a config switch; the baseline path stays untouched.
2. **Stage discipline:**
   - **SMOKE** — minutes; required for any new code path. It proves the pipeline and the artifacts end to end, and nothing more.
   - **PILOT** — the smallest run that can meet, or fail, the row's pre-written criterion. A pilot that can't possibly fail is too small or measures the wrong thing.
   - **FULL** — only after a pilot justified it. State the budget, the expected wall-clock, and the decision the run informs. If the brief lists a `during` checkpoint whose `at` covers full-scale runs, check it before launching: `uv run --with pyyaml python <hub>/newts.py approved <slug> <checkpoint-id>` — exit 0 = approved (follow the PI's note on it: how many runs, how long); nonzero = present the trial results against their promotion criteria and the planned full runs against the budget, end with `needs_pi=<checkpoint-id>`, and stop. Only the PI (or a campaign the PI delegated it to) approves; nothing you write approves it, and full runs launched without it are flagged to the PI. With no such checkpoint, go on. Before any FULL run, also run `uv run --with pyyaml python <hub>/tools/guard.py frozen <slug>` — confirms `eval_frozen` + the PI-owned blocks are intact.
3. **Run** via `scripts/run.py` (long runs: background with output capture). Before a PILOT/FULL run, follow the compute-share rule (hard rule 13): if the lab already runs `compute.max_concurrent_runs` training campaigns (the dashboard's Compute panel, or `newts panel compute`), wait or do CPU-light work. Stage budgets come from `control.yaml` (each run's `budget.max_minutes`); they are instructions the Compute panel tracks, not limits a script enforces — stay within them, and a run needing more budget is a PI flag, not a config tweak. On a machine with a job scheduler (the hub's `compute.scheduler`, set in the dashboard → Settings → This machine & compute), `run.py` **submits** PILOT/FULL runs and **waits** for them — same run dir, artifacts and exit codes (the run's `budget.max_minutes` is the job's time limit); the run shows `status=queued` while it waits (never "stalled"). **Never call `sbatch`/`qsub` yourself**, and follow `SYSTEM.md`'s site rules.
4. **Record** in `EXPERIMENT_LOG.md` (template entry format): outcome with run ids, decision (keep/revert/debug/move on), reasoning. Then **one git commit per attempt** — message `exp-NNN: <one-line outcome>`. If the change isn't kept, revert the code but keep the ledger entry and registry line. (`run.py` already emitted the run's bus events; a kill or stage promotion warrants its own `scripts/lab_bus.py emit` event.) After the append + commit, run `uv run --with pyyaml python <hub>/tools/guard.py append-only <slug>` — confirms the ledger was only appended (never rewritten) and refreshes its baseline.
5. **Update PLAN.md** experiment table (status, result run ids).

## Hard constraints

- **Debug cap:** max `experiment.max_debug_depth` (default 3) consecutive fix attempts on a failing experiment; then record the failure (with diagnosis) and move to the next planned item. Debug from the experiment's *ancestral chain* (its previous attempts), not unrelated history; fix one thing per attempt, and write down the diagnosis even when the fix fails.
- **Frozen things:** eval protocol, test set, seeds policy, budgets. If a result requires touching any of them, stop and flag the PI. Changing the seed/timeout/eval to make a number better — never.
- **Kill criteria:** check PLAN.md's kill criteria after every PILOT. If triggered, stop the loop and present the evidence to the PI — recommendation kill/park, their call (headless: run footer `needs_pi=kill_criteria` with the evidence path in `summary`).
- **Multi-seed:** before any result is treated as a finding (analysis/paper), re-run the winning config at ≥ `seeds.multi_seed_n` (default 3) seeds via `scripts/sweep.py`, report mean ± spread. Seeds come from `seeds.list`; a repeat with new seeds after seeing a result is logged `rerun_of: exp-NNN` with a reason.
- **The test split is read once** (project rule test-once): only the plan's **final evaluation** row evaluates on the held-out split, after selection on validation is finished, and every test read is a row in PLAN.md's "Test-split access log". A second read of the same configuration needs a written reason and makes its result exploratory.
- **Plan drift:** new experiment ideas go into PLAN.md as new rows (with criteria) before they run; run one ahead of planned work only if it is cheaper AND more decisive. A row added after full runs were approved or after the first analysis is tagged `(post-hoc)` (project rule post-hoc-rows).
- **Data provenance:** before the first PILOT, `control.yaml` `data:` names the dataset's source, version, hash, split seed and licence (`scripts/check_project.py` warns while it is empty).

## Parallelism (optional) — the parallel path

Independent configs (a seed sweep, disjoint ablations) may run as parallel background processes or isolated **`experiment-runner`** subagents (model: `agents.runner_model`, tier-resolved; same contract as `/improve`'s parallel path — worktree confinement, result packets, parent-only ledgers). Parallelize only work that doesn't depend on another's result. Ledger entries and commits remain one-per-experiment, written by you after reading each result.

## Exit

When the planned table for the current stage is done (or kill criteria fired), summarize state in `EXPERIMENT_LOG.md`, **distill any durable within-project lesson into `NOTES.md`** (a gotcha+fix, an approach tried-and-abandoned, or a settled result — one line + evidence pointer; the index a future session reads at orientation), and append a lab notebook entry. If the planned questions are answered but the headline metric still needs pushing, don't report yet: continue with `/improve` (same ledger, same rules — its operators generate the next attempts; headless: `next=/improve <slug>`).

## Report the outcome

Only if the brief lists outcomes for you (see above): `uv run --with pyyaml python <hub>/newts.py move <slug> <outcome> --note "…"`.

- `done` — the planned experiments are finished: every row has a result or a recorded failure, and the winning config has its multi-seed result. If the project has a `TARGET.md`, `done` means the target is met or the budget is spent. Note: the headline result with its run ids, or how the budget ran out.
- `park` — the PI chose to shelve it after the kill criteria fired, or it is blocked on something outside the lab. Note: what blocks it and the evidence path.
- `kill` — the PI chose to kill it after the kill criteria fired. Note: the criterion that fired and the evidence path.

If `newts move` says the study waits for the PI, present the results note (the stage's run table and figure; for a target, the best runs) and stop (headless: `needs_pi=<that checkpoint's id>`). Headless footer: `next` is what `newts move` printed.
