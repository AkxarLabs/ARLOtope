# Scope (design deliberation)

<!-- arlotope:contract (generated by `arlo docs` from workflow/) -->

**Finish by reporting one outcome** — `done`, `park`, `kill` — when the brief assigns this skill the task. Use `uv run --with pyyaml python arlo.py move <slug> <outcome> --note "…"`; follow the brief's routes. Never edit the journal or registry.

**It must produce:**
- studies/<slug>/decisions.md (ADR-style, one entry per key decision)
- value re-verification result

**Show the PI** (`python tools/artifact.py publish --title "…" --file <path>`): a design decision you could not settle on the evidence — as a question with the options you weighed (`--question … --choices …`); settled decisions stay in decisions.md. Publish once per milestone. Use `--question "…" --choices "A;B"` for feedback, never approval.

Output: `studies/<slug>/decisions.md` (from `templates/idea/decisions.md`) with every key design decision
deliberated and settled — the raw material `/propose` builds on. Depth knobs: `scoping.*`.

**Advocates are the named `scoping-advocate` role** (`.claude/agents/scoping-advocate.md`, rendered by
`tools/role_sync.py` with `agents.critic_model`/`critic_effort` already resolved). Spawn them with
`subagent_type: scoping-advocate` so the model binding and the dashboard's trace come for free, and start
each spawn's description with the decision + option (e.g. "D-003 tokenizer: BPE"). Backends without role
files: `uv run --with pyyaml python tools/role_sync.py resolve critic` prints the `model=`/`effort=` to
pass per spawn; otherwise advocates run at the session model.

## 1. Enumerate the decision branches

Read `IDEA.md` (with its reflection summary), `lit-review.md` (especially positioning) and any
`/discuss scope` session docs in `studies/<slug>/sessions/`, whichever exist. A session doc is the
PI-settled starter list; never re-derive a decision the PI already framed. Otherwise list every decision
that shapes the project, typically:

- **Problem framing**: the exact question, the scope boundaries, what is explicitly out.
- **Dataset / benchmark**: which one, the split policy, licensing and availability.
- **Model family & scale**: what to run at pilot vs full, and what scale the claim needs.
- **Baseline set**: the baselines the field will demand (from the lit review's positioning).
- **Primary metric + eval protocol**: the metric, the val/test design, the seeds policy.
- **Method recipe**: the core technical choices inside the proposed method.
- **Ablation axes**: which components get removal tests.
- **Compute plan**: stage budgets, and what fits the hardware.

Add branches specific to this idea and drop irrelevant ones. Order them by how much of what follows each
constrains, framing first.

## 2. Deliberate each branch — in order

1. Generate `scoping.options_per_decision` genuinely distinct options. An option you would never pick is
   filler; replace it.
2. Argue each option before choosing:
   - **With advocates** (`scoping.advocate_subagents` set): one `scoping-advocate` per option, in
     parallel. Each gets a fresh context — the hypothesis, the lit positioning and its option, never your
     leaning — and one charge: *argue the strongest case for this option AND name its two most likely
     failure modes.*
   - **Without advocates:** argue each side yourself, in writing.
3. Record the decision as a D-NNN entry in `decisions.md`:
   - a written rationale, a **rejected-because** line per alternative, and a **revisit-if** condition
     written so a later session can check it mechanically against run artifacts;
   - **`Headline: yes`** if the choice is load-bearing for the central hypothesis the project's novelty
     rests on (typically only the method recipe and the framing); else **`Headline: no`**. This flag is
     the autonomy boundary downstream: an `explore`-mode loop may reopen a `Headline: no` decision itself
     when its revisit-if trigger fires, but reopening a `Headline: yes` one escalates to the PI;
   - for a settled `Headline: no` decision, the **`Revisit predicate:`** line, the machine-checkable form
     of its `Revisit if:` trigger (grammar + example in the template).

   Decisions are append-only once the proposal is approved: reopening one is a new entry referencing the
   old.
4. Lint: `uv run --with pyyaml python tools/guard.py decisions <slug>` (BLOCKS on a malformed predicate;
   WARNs on a missing one).

A decision that genuinely cannot be settled without data may be left **OPEN** with the pilot experiment
that will settle it named — at most `scoping.max_open_questions`. `/propose` turns each OPEN decision into
a pilot row.

## 3. Value re-verification

With every decision on the table, step back and ask, adversarially:

- **Still novel?** Do the settled choices land on something the closest prior work already did? Check the
  lit-review notes, not memory.
- **Still valuable?** With this dataset, scale and metric, would a sceptical reviewer call the eventual
  result meaningful, or "toy setting, unsurprising"?
- **Still feasible?** Do the compute plan and the budgets cover the experiment table this implies?

This is the cheapest place to stop a doomed project — stopping here is success, not failure.

## 4. Report the outcome

Summarize the decision list (one line each), the open questions and the value verdict, then
`arlo.py move <slug> <outcome> --note "…"`:

- `done` — every answer above is "yes" and no more than `scoping.max_open_questions` decisions are OPEN.
  Note: the number of decisions, the OPEN ones, and the headline choice.
- `kill` — any "no" that won't change. Record the reason in IDEA.md and harvest surviving threads into
  `lab/knowledge/OPEN-QUESTIONS.md` (`FAILURES.md` only if scoping produced a substantive negative finding
  worth transferring). Note: the reason.
- `park` — not ready now but maybe later (e.g. more OPEN decisions than the cap allows, or a dependency
  that isn't available yet). Note: what would make it ready.

If `arlo move` says the study waits for the PI, present the decision summary and stop (headless:
`needs_pi=<that checkpoint's id>`).
