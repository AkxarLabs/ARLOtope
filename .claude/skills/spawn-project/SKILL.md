# Spawn Project

<!-- arlotope:contract (generated by `arlo docs` from workflow/) -->
**First, load the brief:** `uv run --with pyyaml python arlo.py brief spawn-project --study <slug>`; skip when `ARLOTOPE BRIEF /spawn-project` is already supplied. Follow its task ownership, additions and checkpoints.

**Finish by reporting one outcome** — `done`, `scaffold-failed`, `park`, `kill` — when the brief assigns this skill the task. Use `uv run --with pyyaml python arlo.py move <slug> <outcome> --note "…"`; follow the brief's routes. Never edit the journal or registry.
<!-- /arlotope:contract -->

Prepare the study's project and verify it before experiments begin.

## Existing repository

Read the registered project path and IDEA.md first. Keep an attached repository's code, environment,
runner and layout; do not run the scaffolder or replace its registered path. Add tracking files only
when requested and explain the additions. Use its own checks, then report the agreed setup's outcome.
The remaining steps are for a new generated project.

## New project

1. Read `studies/<slug>/proposal.md` and relevant decisions/literature notes. If the required proposal
   is absent, report the gap and `park`; do not invent it.
2. Resolve `lab.projects_root` from configuration (default `../arlotope-projects`, relative to the hub).
   Projects live outside the hub as independent repositories. Choose a project type from
   `templates/project-types/*/TYPE.md` and an optional domain profile. Use the PI's confirmed choice
   from the proposal; otherwise present the suitable choices and ask. A new type is a PI-owned design.
3. Run the existing scaffolder:

   ```bash
   uv run --with pyyaml python tools/spawn_project.py --slug <slug> --title "<title>" \
     --project-type <type> [--domain <domain>] [--overlay compete]
   ```

   It substitutes template values, installs the type/domain files and harness resources, copies any
   Lab SYSTEM.md and registers the project path. It refuses an invalid study position or a reused
   committed/nonempty-run project. On refusal, stop and show its error; do not bypass it.
4. Fill `control.yaml` from the proposal: budgets, data provenance, seeds and loop settings. Choose
   `runner: python-import` for Python work or `shell-command` with `runner_command` for other tools;
   the latter must write its metrics to `$RUN_DIR/result.json`. Follow TYPE.md's definition of staged
   scale and replication. Use `--overlay compete` for target-driven projects.
5. Fill PLAN.md from the approved design: headline hypothesis, frozen evaluation and analysis plan,
   staged experiments with prewritten criteria, ablations and kill criteria. Reference budgets in
   control.yaml rather than duplicating values. Keep loop mode `execute` unless the PI or approved
   campaign has authorized `explore` and its caps. Full runs retain their configured checkpoints.
6. Add only the real project dependencies to pyproject.toml; retain the default package name unless
   there is a reason to change it. Adapt the tiny smoke to the selected type: regression, simulation,
   proof checker or training as appropriate.
7. Initialize Git and run `uv sync`, the smoke (`scripts/run.py --config
   configs/experiments/exp-001-smoke.yaml`), `uv run pytest tests/` and
   `uv run --with pyyaml python scripts/check_project.py`. Require green results before committing
   the scaffold with uv.lock. After `experiment.max_debug_depth` unsuccessful fixes, leave it
   uncommitted and report `scaffold-failed` with the failed check and error.
8. Record setup and useful environment lessons in the notebook/project NOTES.md. Do not start
   domain experiments in this run; the next workflow task owns them. Keep the toy smoke working
   until the first real experiment replaces it.

## Finish

Report the project path, actual check results, configured budgets and first planned experiment.
Report the brief's outcome once: `done` for committed, verified setup; `scaffold-failed` for exhausted
setup debugging; `park`/`kill` only with the relevant reason and evidence. Preserve all existing work.
If the kernel waits at a checkpoint, show what needs review and use its checkpoint ID in `needs_pi`.
Use `other` for an unresolved setup decision with no checkpoint; never invent an approval.
