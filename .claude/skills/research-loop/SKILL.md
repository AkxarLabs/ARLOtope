# Research Loop (unattended operation)

<!-- arlotope:contract (generated by `arlo docs` from workflow/) -->
**First, load the brief:** `uv run --with pyyaml python <hub>/arlo.py brief research-loop --study <slug>` (`<hub>` = this project's `control.yaml` `hub_path`); skip when `ARLOTOPE BRIEF /research-loop` is already supplied. Follow its task ownership, additions and checkpoints.

**Show the PI** (`python "$ARLOTOPE_HUB/tools/artifact.py" publish --title "…" --file <path>`): a cycle report when the loop stops, or every few cycles on a long loop (what was tried, what is best so far) — never every cycle. Publish once per milestone. Use `--question "…" --choices "A;B"` for feedback, never approval.

**Read first:** `<hub>/AGENT-GUIDE.md` — "Unattended loops (/research-loop)", "In-project iteration: execute and explore".
<!-- /arlotope:contract -->

Run experiment cycles in the project, using `control.yaml` (`loop.*`, `budgets.*`) over Lab defaults.
The loop reuses `/experiment` and `/improve`; it does not replace their methods or complete their
workflow task for them.

## Enter or resume

1. Read `LOOP_BRIEF.md`. If missing, draft it from the proposal using `templates/loop/LOOP_BRIEF.md`;
   request the missing budget/decision and stop. Never invent authorization or a budget.
2. Find any configured `during` checkpoint covering unattended loops. Check
   `arlo.py approved <slug> <checkpoint-id>` before spending. If unapproved, present the brief,
   report that checkpoint as `needs_pi` and stop. With no such checkpoint, no approval is required.
3. Use the authorized `execute` or `explore` mode: the approval note, then the brief, then `loop.mode`.
   Do not switch modes yourself. Approved brief content above its Loop Log stays frozen.
   Other unapproved checkpoints can block particular work without blocking unrelated in-bounds work.
4. Run `scripts/reconcile.py` before new work. Use `--fix` only to clear a confirmed stale loop lock.
   A heartbeat in `.bus/.loop-active` newer than `2 × loop.monitor_poll_seconds` means another loop
   is live: stop. Otherwise claim it, refresh it during monitoring and clear it on exit.
5. Check in-flight runs: monitor live processes rather than duplicating them; record dead attempts.
   Reconcile registry/ledger run IDs and add missing completion/Loop Log entries after a crash.
6. Load the `/experiment` and `/improve` briefs once; refresh them on a loop lasting over a day.
   Read `SYSTEM.md` if present and run `<hub>/tools/guard.py frozen <slug>` before spending.

Use the project's `control.yaml` `hub_path` for `<hub>` commands. Re-entry is the same procedure
regardless of harness; do not assume a native `/loop` command exists.

## Each cycle

1. Read `NOTES.md`, PLAN.md, recent experiment/Loop Log entries, registry and git history. Check and
   acknowledge the project's directive inbox within the protocol. Avoid repeating known dead ends.
   In explore mode, inspect `decisions.md` revisit predicates against artifacts when that file exists.
2. Select work in order: unfinished plan rows, ablations, multi-seed confirmation, then the ordinary
   `/improve` operators. Use the prewritten criteria, project type and frozen evaluation policy.
3. In explore mode, if ordinary work is exhausted, read `/improve`'s `references/explore.md`:
   try bounded expansion, then evidence-triggered revisits. Respect expansion/line caps and the
   headline boundary; a plan-trace BLOCK routes to `/propose`, not an in-place headline change.
4. Check fit before launch. The run's `budget.max_minutes` must fit remaining loop wall-clock and
   project budget. Work covered by a checkpoint also needs its approval and must fit its note.
   Record blocked or unaffordable work as a PI note. If nothing fits, stop rather than idle.
5. Launch through `scripts/run.py` or `sweep.py`. Check shared compute before PILOT/FULL work.
   If occupied, do useful CPU-light work and retry. When configured, run.py handles scheduler
   submission and waiting; do not call `sbatch`/`qsub` directly. Queued work is alive, not stalled.
6. Monitor only with
   `python scripts/status.py <run_id> --watch --log-interval <monitoring.log_interval_seconds> --poll <loop.monitor_poll_seconds>`.
   For a sweep, omit the ID to follow its latest run. No intermediate log reading or partial-curve
   reasoning. On terminal status, record the result; after two consecutive stalls, diagnose and stop
   the owned failed process. Keep the loop heartbeat current.
7. Append the attempt's ledger entry with parent/operator fields, commit it, update PLAN.md and
   append a Loop Log row: action, run IDs, best metric, progress and notes. Emit `cycle`.

## Stop and escalation

- Continue while useful work fits and no stop condition holds. A clean negative resolving a planned
  question counts as progress; a crash does not. `loop.no_progress_backoff_cycles` without progress
  stops the loop with a diagnosis. Check kill criteria each cycle; a fired criterion stops it.
- Execute mode stops at plan exhaustion. Explore mode first uses its bounded expansion opportunity;
  it still stops at budget, round caps, kill criteria or no-progress backoff.
- If loop wall-clock expires during a run, let that run finish within its own budget, record it and
  exit. Launch nothing new after expiry.
- Frozen problem/eval/test/seeds/budgets never change here. Follow `/improve`'s headline-change
  boundary. Queue the PI decision and emit `scripts/lab_bus.py escalate --detail "<what and why>"`
  when a change needs authorization. A campaign may use only its explicit bounds and required
  overseer checks. Continue unrelated work within bounds when permitted.
- Record revisits/expansion in PLAN.md's Re-planning log and decisions.md. Emit `replan` and any
  `approach_ideate` event when it happens, not only when the loop ends.

## Exit

Clear the loop lock and append a final Loop Log row with the stop reason. Summarize tried, kept and
abandoned work with artifact pointers in EXPERIMENT_LOG.md; distill durable local lessons into NOTES.md.
At strict oversight, have an evidence-only overseer check each claimed-progress row. Complete the hub
notebook/knowledge write-back and run `<hub>/tools/guard.py writeback <slug>`.

The PI report gives the best supported result, queued decisions, spend and recommended next action.
The owning step's procedure reports its outcome; this loop does not call `arlo move`. Name that
procedure from `arlo.py next <slug>` and explain what its evidence supports. In a headless footer,
`next` is that procedure's command; `needs_pi` is the actual waiting checkpoint, `kill_criteria` or
`none`. If no checkpoint exists but the brief needs a decision, use `other`, not an invented ID.
