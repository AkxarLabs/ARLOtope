# Analyze

<!-- arlotope:contract (generated by `arlo docs` from workflow/) -->
**First, load the brief:** `uv run --with pyyaml python arlo.py brief analyze --study <slug>` — skip it if a `ARLOTOPE BRIEF /analyze` block is already in your context. It says where the study stands, the PI's own instructions for this work, and the checkpoints.

**Finish by reporting one outcome** — `done`, `more-experiments`, `null-result`, `park`, `kill` — with `uv run --with pyyaml python arlo.py move <slug> <outcome> --note "…"`. The study's workflow decides where it goes (the brief lists each outcome's destination); never edit lab/REGISTRY.md or lab/journal.jsonl.

**It must produce:**
- an analysis entry (verified against run artifacts) in the study
- findings distilled to lab/knowledge
- an outcome: done | more-experiments | null-result | park | kill

**Show the PI** (`python tools/artifact.py publish --title "…" --file <path>`): the headline findings (each with its run ids) and the key figure, with your outcome in the note. One artifact for what they would genuinely want to see — not a running commentary. A decision you need takes `--question "…" --choices "A;B"` (the answer comes back to this run); it is never an approval.

**Read first:** `AGENT-GUIDE.md` — "The back half: analysis, writing, review and back" (it binds exactly like AGENTS.md).

Reads a project's results — when its experiments are done, or mid-way for an interim read. Output: an analysis written into the project + distilled knowledge in the hub + an outcome.

This procedure can also run at a step whose own procedure is another one (an interim read). Report an outcome only if the brief's "When your work on this step is done" section lists outcomes for you; if it says you run alongside the step's own procedure, write the analysis, add any missing rows to PLAN.md, and just finish.

The interpretive step is where AI-written research is weakest. Slow down here.

## Procedure

1. **Reconstruct from artifacts only.** Load `runs/registry.jsonl` and the relevant `runs/<id>/metrics.json`. Every number in the analysis carries its run id. If a remembered result has no artifact, it does not exist.
2. **Answer the proposal's questions.** Go row by row through PLAN.md's experiment table: was the pre-written criterion met? Compute effect sizes against the baseline with the spread the project's `TYPE.md` prescribes (seeds for `ml`, bootstrap for `empirical`, draws for `simulation`, N/A for `theory`). The rules:
   - Use the pre-written comparison and uncertainty method. Overlapping or non-overlapping seed
     spreads alone are not a decision rule. If the planned evidence criterion is not met, report
     the comparison as inconclusive rather than treating the best run as a confirmed finding.
   - Be explicit about which comparisons were selected on validation, and confirm from PLAN.md's "Test-split access log" that the test split was read once per configuration, by the final-evaluation row (project rule test-once).
   - **Follow the frozen Analysis plan** (PLAN.md): apply its primary comparison, uncertainty method and exclusion rules as written, and map the outcome onto its decision rule (supports / refutes / inconclusive → the pre-agreed action). Anything the plan did not name is **EXPLORATORY**: say so in the analysis note, and carry the label into the paper (project rule analysis-plan).
   - Report the number of configurations evaluated on validation to reach the headline result (the registry has them); the paper's appendix states it.
3. **Interrogate the result:**
   - **Alternative explanations.** Could the gain come from a confound: extra compute, parameters or data, an eval artifact, lucky seeds?
   - **Load-bearing ablations.** Which ablations from the plan are now load-bearing? Are there kept but never-ablated changes stacked in the winning config?
   - **Try to break it.** What is the cheapest experiment that could break the favoured interpretation?
   - **Founding assumptions.** If `studies/<slug>/decisions.md` exists, ask whether the evidence now meets any settled decision's `Revisit if:` trigger — a design choice made earlier that now looks wrong.

   Then run the **oversight pass** (`oversight.level` ≠ off): spawn one `overseer` subagent (`support` check) per headline interpretation, giving it the statement + artifact paths only. OVERREACH → adopt its supported version verbatim; UNSUPPORTED → it is not a finding, whatever it felt like.
4. **Decide:**
   - **Missing ablations / confound checks** → add the rows to the project's `PLAN.md`, commit the project, and emit `uv run python tools/lab_bus.py emit replan --idea <slug> --detail "analyze → more experiments"`. (Ablations are complete when every row of PLAN.md's ablation plan has a multi-seed result or a recorded failure — no kept change without its removal test.) Outcome: `more-experiments`.
   - **A settled decision's `Revisit if:` trigger is now met** → reopen it via `/improve`'s `revisit` operator (new `D-NNN`, dependent lines → `retired-by-revision`, seed replacements). A `Headline: no` decision is autonomous (overseer-gated); a `Headline: yes` decision escalates to the PI. Under an `explore` research loop the loop does this itself; in a manual `/analyze`, recommend it (or do it if non-headline and you're continuing). Outcome: `more-experiments`.
   - **Hypothesis confirmed with an honest effect** → outcome `done`.
   - **Null/negative** → it can still be a paper, and the PI decides: outcome `null-result`. Only when the evidence leaves nothing worth reporting, `kill` or `park` with reasons. After a kill, emit `uv run python tools/lab_bus.py emit kill --idea <slug> --detail "<reason>"`, then run `uv run --with pyyaml python tools/guard.py evolve <slug>` — a BLOCK means the kill left no CORRECTION; write the `FAILURES.md` / `NOTES.md` entry before moving on.
5. **Write it down:** `analysis-YYYY-MM-DD.md` in the project root (claims → run ids throughout). State the headline result together with its uncertainty; name the interpretation risks plainly, and the evidence that would resolve each one. Distill to the hub: `FINDINGS.md` (confirmed, with evidence pointers), `FAILURES.md` (what didn't work + diagnosis), `OPEN-QUESTIONS.md` (new threads). A durable *settled-here* or *abandoned-here* conclusion also belongs in the project's `NOTES.md` (the local "don't re-derive this" cache, in addition to the hub promotion). Append a lab notebook entry.
6. **Report to the user:** the headline result (with uncertainty), the interpretation risks, and the outcome you chose.
7. **Report the outcome** — only if the brief lists outcomes for you: `uv run --with pyyaml python arlo.py move <slug> <outcome> --note "…"`.
   - `done` — the hypothesis is supported with an honest effect, and the ablation plan is complete. Note: the headline result with its uncertainty and run ids.
   - `more-experiments` — the analysis needs runs the plan doesn't have yet; the new rows are in PLAN.md. Note: which rows and why.
   - `null-result` — the hypothesis is not supported (null or negative). Note: the measured effect with its uncertainty, and whether you think it is worth writing up.
   - `park` / `kill` — nothing worth reporting, or blocked outside the lab. Note: the reason and the evidence path.

   If `arlo move` says the study waits for the PI, present the headline findings (each with its run ids) and the key figure, and stop (headless: `needs_pi=<that checkpoint's id>`). If it says the PI decides where the outcome leads, present the same and stop. Headless footer: `next` is what `arlo move` printed.
