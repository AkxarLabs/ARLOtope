# The agent guide — read the part that applies

`AGENTS.md` is what every agent needs in every session: the lifecycle, the checkpoints, the hard rules. This guide
is the reference it points to — read a section when your work touches it (your procedure's contract or
brief usually says which). Everything here binds exactly as if it were in `AGENTS.md`; it lives here only
so that agents who don't need it don't carry it in every session.

## Target-driven projects (/compete)

**Target-driven projects (`/compete`).** Not every project is a paper. When the task has a **fixed, straightforward target** — a benchmark to beat, a metric to hit, a leaderboard to climb, an internal KPI — `/compete` spins off a project that enters **directly at `active`** and iterates toward the target. It reuses the whole engine (staged scale, frozen eval, budgets, ledger, git, `/experiment`, `/improve`, `/ideate --in-project`, `/research-loop`) and **skips the paper layer**: `/ideate→/lit-review→/scope→/propose` are recorded `N/A (target-driven)` in `IDEA.md` (the `/compete` interview sets the target and its budget; the `target` workflow's checkpoints apply), there is no novelty gate, and — crucially — **no headline-hypothesis boundary**, so the method space is fully open: model/feature/approach changes and `/ideate --in-project` are all in-bounds, the main way ideas fan out toward the metric. The **frozen set is reinterpreted** as `{the task data/resources, the metric + direction, the output contract, the rules, the deadline}` (`eval_frozen: true` still holds — the metric + local validation split is the frozen eval; selection discipline binds *harder*, since an external scorer **is** the held-out test). Nothing is host-specific — Kaggle is one instance the agent adapts to. The PI-owned brief is `TARGET.md` (machine mirror: `control.yaml` `target:`); close out with `/finalize` (reproducibility pass on the winning run). See the `/compete` skill and `docs/compete.md`.

## In-project iteration: execute and explore

**In-project iteration has two modes** (set by the loop's `LOOP_BRIEF.md` `Mode:`, default `loop.mode: execute`). `execute` runs the approved `PLAN.md` and stops when exhausted. `explore` is the autonomous in-project iterator: when the plan is exhausted with budget left, it may **expand the frontier** (propose results-grounded new experiment lines) and **reopen a non-headline design decision** (`decisions.md` whose `Revisit if:` trigger fired) — re-planning *within* `active` (no new lifecycle state; `active → active`), inside the frozen set and the budgets, capped by `loop.explore_*` and the anti-burn backoff. **Frontier-`expand` is incremental iteration WITHIN the headline hypothesis — it is NOT divergent method-ideation;** generating a genuinely new *approach* to the problem is `/ideate --in-project <slug>` (see Lifecycle's in-project ideation note and the `/ideate` skill). The autonomy boundary is mechanical: reopening a **`Headline: yes`** decision (the central hypothesis the proposal's novelty rests on), touching the frozen set, or exceeding the budget escalates — a PI note, or under a campaign the PI approved the same brief bounds + overseer `support` check the campaign uses before it asks the keeper to approve a checkpoint. A `Headline: yes` reopen is not a dead end: it **routes to in-project method-ideation** — `/ideate --in-project <slug>` (under `ideation.in_project_approval`) or a successor hub `/ideate` — never a bare dead-end PI note. Selection discipline (hard rule 5) binds *harder* during exploration: every expanded line still tunes on validation, reports on the frozen test, and needs multi-seed before a paper claim. A pivot is never silent — it lands in `decisions.md`, PLAN.md's Re-planning log, and the bus.

## The back half: analysis, writing, review and back

**Back-half round-trip (`analysis` → `writing` → `internal-review`, and back).** The paper phase runs in a **HUB** session that reads the project's artifacts *across the boundary* (the study's project path is in `arlo studies`; `runs/`, `claims.yaml` evidence, and figures resolve through it). When `/analyze` or `/review-paper` produces a NEEDS-EXPERIMENT item or a new ablation, route it back to the project as **ONE coordinated cross-repo step**: append the rows to the project's `PLAN.md` (with pre-written criteria), commit the project and emit `replan`, then report the outcome that says so (`more-experiments`) — the workflow routes the study back to its experiments. The project may be re-entered **multiple times** across the paper phase; each round is a route the workflow names, never a step it doesn't have. `/finalize` revisits the project once more for the reproducibility pass (and secures the cited artifacts into the hub).

## In-project method-ideation (/ideate --in-project)

**In-project method-ideation (`/ideate --in-project <slug>`).** The one first-class way to ideate *divergent* new approaches **inside** an active project. It reuses `/ideate`'s generate → fresh-context critic ensemble → tournament → triage, but scoped to **method approaches within the project's FROZEN set** (problem/eval/test/seeds/budgets — never touched; `active → active`, no new lifecycle state). Its output is **candidate approaches, not experiments**, capped by `ideation.in_project_candidates`/`ideation.in_project_rounds`. **Checkpoint discipline:** a surviving approach that would change the **headline hypothesis** must re-enter `/propose` (a mini-proposal — new hypothesis framing + kill-criteria + budget) **or** spawn a successor hub idea (`/ideate`); it **never** enters experiments on a bare PI note — this preserves the `Headline: yes` autonomy boundary, and only a `/propose` re-entry reaches the proposal's checkpoint again. **Two independent PI-owned switches control it:** the ENABLE flag `ideation.in_project` (a kill-switch — `false` turns the `--in-project` capability OFF, and every router that would reach it must then fall back to a successor hub `/ideate`) and the APPROVAL knob `ideation.in_project_approval` (**campaign-scoped** — it only changes behavior under a campaign the PI approved; manual runs always wait for the PI). **Approval** (`ideation.in_project_approval`): manual/PI-driven runs wait for the PI (surviving candidates queue at `/propose` for the PI's approval of the proposal); under an approved `/autopilot` campaign the default is auto-approval **within the brief's bounds + the overseer `support` check** the campaign already uses before it asks the keeper to approve a checkpoint (the campaign brief/config may override to require-PI). Incremental `expand` is unchanged and stays the only autonomous, within-hypothesis generator. No working agent approves its own checkpoint: the PI does, the explicitly configured independent gate reviewer returns a verdict for the engine, or — only for a checkpoint the PI delegated to a campaign on the campaign form — the executor's campaign keeper records it after re-running the checkpoint's checks itself.

## Event bus & directives

Attached projects need no copied scripts. Use the hub's `tools/lab_bus.py --project
"<project-path>" inbox` (or `ack`) for their directives. Executor runs receive a scoped bus
environment and the correct footer command in their brief, including for unscaffolded repositories.

**Event bus & directives (optional, powers the dashboard).** A file-based, append-only signal stream the optional dashboard reads (`tools/lab_bus.py`; runs append to `lab/.bus/events.jsonl`). It is best-effort and never required — but when you stop at a checkpoint, kill an idea, run a review, or write back, emit a one-line event (`arlo move` records a study's moves itself): `uv run python tools/lab_bus.py emit <kind> [--idea X] [--detail "..."]` (kinds listed in `docs/dashboard.md`). And at every pause point — session orientation, each loop/campaign cycle, each experiment attempt, `/advance` selection — run `tools/lab_bus.py inbox`: a PI **directive** there is an instruction to act on within the protocol (it can steer priorities, request runs *within* the budget and the approved checkpoints, park/kill, answer an open question, stop a loop), then ack it `done` with an evidence pointer. A directive that would touch frozen/PI-owned settings (budgets, evals, approvals) is acked `blocked` with the reason — **directives are subordinate to checkpoints and hard rules; a directive is never an approval.**
  - **Structured commands.** The dashboard can issue a directive carrying `kind:"command"` + an `action` (`start_loop`, `stop_loop`, `set_mode`, `run_smoke`, `request_run`, `prioritize`, `park`, `kill`, `analyze`, `ideate`) and `args` — `inbox` renders these. Execute the action through the normal procedure for it, within the protocol; ack `done`/`blocked` exactly as for a free-text directive. A command is still never an approval and never overrides a frozen/PI-owned setting. With the executor on, the dashboard ALSO launches the procedure that consumes the command (`run_smoke`/`request_run` → `/experiment`, `start_loop` → `/research-loop`, `analyze`, `ideate`), so the command is in that run's inbox at its first checkpoint.
  - **Approvals are records, not prose.** The PI approves a checkpoint on its Permit sheet in the dashboard, or with `arlo approve <study> <checkpoint>`; a campaign the PI approved may record a checkpoint the PI delegated to it, through the executor's keeper. Each decision (approved, changes-requested, revoked) is one event in `lab/journal.jsonl`; campaign briefs (`campaign:<name>`) are approved the same way. Nothing you write in a document approves anything, and you never write the journal or run `arlo approve`/`revoke` (the signature guard refuses, and so does the kernel inside a run). To see whether a checkpoint is approved, read your brief or run `uv run --with pyyaml python arlo.py approved <slug> <checkpoint-id>`. Approving a `before` checkpoint moves the waiting study on; the dashboard, `arlo approve --start` or the keeper can start the new step's procedure in the same act, and the executor won't start a step's procedure for a study that isn't standing at that step.

## Mechanical guards (tools/guard.py)

**Mechanical checks (`tools/guard.py <check> <slug>`).** The highest-risk rules are not only prose — run the lab's checks (`checks/*.py`) at the risky points and "remember to X" becomes "can't proceed unless X": `guard.py frozen <slug>` (`eval_frozen` + the PI-owned blocks intact), `guard.py append-only <slug>` (the project ledgers were only appended, never rewritten), `guard.py writeback <slug>` (rule 11 done), `guard.py evolve <slug>` (rule 11's triggered operators fired: a kill left a CORRECTION, a results-stage exit left a RECIPE), `guard.py decisions <slug>` (every settled non-headline `decisions.md` decision carries a machine-checkable **Revisit predicate**), `guard.py plan-trace <slug>` (every non-baseline `PLAN.md` row traces to a `D-NNN`/`(expand Rn)` origin; a `Headline-change: yes` row bypassing `/propose` is blocked), `guard.py full-runs-without-approval <slug>` (no FULL run started before its checkpoint was approved). Exit **0 = proceed · 1 = blocked · 2 = warn**. Where a study may go is the kernel's (`arlo move` refuses what the workflow doesn't allow, and holds a study at an unapproved `before` checkpoint); a check **never grants an approval** — the checkpoints and hard rules still bind exactly as written.

## SYSTEM.md — the machine experiments run on

**SYSTEM.md (optional, PI-owned):** the PI's description of the machine/cluster experiments run on — hardware, data locations, scheduling rules, forbidden actions. Lab default at `lab/SYSTEM.md` (offered by `/setup-lab`; template `templates/SYSTEM.md`), copied into each project at spawn. If present, its constraints bind every agent and subagent like `control.yaml`; agents never edit it. Absent means "no constraints beyond this protocol".

## Traceability hooks

**Traceability hooks (optional, fail-safe).** The lab also runs best-effort traceability hooks (`.claude/settings.json` → `tools/trace_hook.py`) that log each agent/subagent's tool actions to per-worker logs under `.bus/workers/`. They are best-effort and **never block a tool call**; the logs are local/disposable. The harness writes them — agents do not — so the parent-only-ledgers rule (subagent rule 3) is untouched.

## Programmatic agents

**Shared knowledge.** Notes, saved workspace answers and retained sources are ordinary Markdown
records, normally in project `.arlotope/knowledge/`. Use the knowledge command supplied in the run
brief to list/search/read and acknowledge requested human notes. Reading acknowledgement does
not queue work or grant approval. Preserve source coverage (metadata/abstract/sections/full text)
and provenance when recording literature. See docs/knowledge.md.

**Assignments.** A task's role supplies instructions; `agent.preset` selects a saved harness/model;
`context` selects fresh, continued or forked conversation. Lab and study role defaults apply only
when the task does not pin a selection. Continue/fork retains the captured source configuration.
Use declared causal sources; never pick an unrelated recent run. Independent review starts fresh
with author-summary handoff off. Assignment files are researcher-owned. See docs/agent-workflows.md.

**Workflow history.** `tools/study_history.py <study>` reads recorded task passes, owning sessions,
available attempts, workflow decisions and output references. `--save` refreshes generated Markdown
and JSON under `studies/<study>/history/` for the Library. These snapshots are not a new journal or
approval source. Read original evidence and available transcripts; old/missing child records and
offline remote mirrors do not establish complete coverage. Managed runs also retain exported responses and human exchanges in `<run>.d/conversation.jsonl`. Use `arlo log "<finding or decision>" [--tag label] [--ref evidence-path]` for useful context; the run supplies study and attempt. Logs never complete tasks or approve checkpoints. See docs/agent-workflows.md.

**Configured independent gate reviews.** A published checkpoint may explicitly use `approver: agent`.
The ordinary executor launches a fresh reviewer with the declared evidence, rubric and review skill;
the engine validates its JSON decision, evidence revision, task visit and checks before recording it
and applying the named route. The reviewer must not move the study or approve work directly. Existing
researcher/campaign checkpoints keep their policies until explicitly edited and published. A completed
model turn alone does not complete a workflow task: report the accepted outcome. When stopping at a
during-task gate, report its checkpoint ID as `needs_pi`; the configured reviewer can then be queued.
See docs/agent-workflows.md for context, skill sequences, forks, loops and export.

**Programmatic agents (optional, PI-owned, OFF by default).** The executor (`tools/executor/`, used by the dashboard and by `tools/executor_cli.py`) runs a procedure — or the PI's free-form instruction — as a **headless top-level session** (native Claude/Codex/opencode, or optional ACP; `agents.programmatic.backend`) in the hub or a project repo: **not a nested subagent**, so it can itself spawn experiment-runner subagents. This is how the lab works several projects at once, coordinated through the bus, the approvals and the budgets. It is **under the PI's control**: refused unless the PI set `agents.programmatic.enabled: true`; **depth-capped** (`max_depth`, default 1 — a launched agent can't launch more); each run **inherits every checkpoint** (it stops at one that isn't approved; only the PI, or a campaign the PI approved through the executor's keeper, approves one). Each run has a durable record, captured transcript and bus events under `<bus>/agents/`; supported harness tracers also record observed subagents. Transcripts may be capped and child coverage varies by harness; use `executor_cli.py evidence <run>` to inspect available paths and gaps. `executor_cli.py explain <run> [--agent <child>]` starts a separate terminal explainer from those records, without resuming the source session. The PI can **stop** any run live (the dashboard, `arlo stop <id>`, `executor_cli.py stop`, a bus `kill`/`park` directive), **hold** one study (`arlo hold <study>`: nothing new starts for it), or **pause** the whole lab (`arlo pause` / `arlo resume`). See `docs/autonomy.md`.

## Headless runs under the executor

**Backend boundary:** native Claude/Codex/opencode transports and optional ACP v1 use the same run
and workflow model. Guards are installed where the harness supports them; ACP file/terminal calls
provided by Lab run the applicable guard. An ACP agent may also own tools that do not traverse those
client calls. This is protocol and permission discipline, not an OS sandbox. Advertised ACP capabilities
do not imply native slash commands, fresh-context subagents or session forking. Use the backend's
supported mechanism or an explicit evidence handoff; never claim context isolation from prompting alone.

**Published work:** use `tools/artifact.py` for reports and visual summaries. Remote runs receive a
publisher wrapper in their instruction snapshot; it forwards to the owning Lab rather than creating
another journal or dashboard. A Results reply is feedback, not approval. See `docs/artifacts.md`.

**Headless runs under the executor (dashboard task launches · `tools/executor_cli.py`).** The same master switch also lets the PI launch any **whitelisted** procedure as a headless session from the dashboard — hub-level (`/propose x`, `/advance`, `/autopilot continue <brief>`, …) or project-level (`/experiment`, `/improve`, `/research-loop`) — each in its own detached supervisor (`tools/executor/`), watched live, paused and resumed on the PI's answers, stoppable — or the PI's own **free-form instruction** ("Ask agent", skill `ask`). A step's procedure runs only for a study standing at that step, and nothing starts for a study a flag holds. **Supported harness tool hooks carry the signature guard** (`tools/signature_guard.py`, a PreToolUse hook): it denies any write to what only the PI may change — the journal and the registry generated from it, the other PI records, `lab/config.yaml` (except in `/setup-lab` and `/configure`), the lab's procedures, roles, checks, workflows and rules — and shell commands that do the same or run `arlo approve`/`revoke`. A denial means: ask the PI (or suggest a change with `arlo propose <procedure> --file <draft.md>`). It is a speed bump, not a vault: what a run does is on its digest for the PI either way. When `ARLOTOPE_RUN_ID` is in your environment you are such a run, and two extra rules bind you: **(1) One question, then stop.** When the procedure needs a PI decision, ask it with ONE `AskUserQuestion` call (concrete options, your recommendation first) as the only tool call in that turn — the run pauses and you are resumed with the PI's answer; a question with no discrete options goes in plain prose as your final message (the PI's reply resumes the session). Backends without `AskUserQuestion`: `lab_bus.py escalate`, state the question, end. **(2) The run footer.** Before ending any turn in which the procedure finished or stopped, emit `lab_bus.py emit run_report --data next="<exact next command, or empty>" --data needs_pi=<none|<checkpoint id>|kill_criteria|null_result|spawn_type|other> --data summary="<≤200 chars>"` (the run id is taken from `ARLOTOPE_RUN_ID`); when you stopped at an unapproved checkpoint, `needs_pi` is its id and you add `--data study=<slug>`. The footer is how the dashboard knows what you need without parsing prose; a `next` it can launch becomes a one-click button (or, if the PI chose `chain`, the next run — never past an unapproved checkpoint). Neither rule relaxes anything above: a question is never an approval, and a directive or an answer never overrides a frozen/PI-owned setting.

## Unattended loops (/research-loop)

- A loop requires a `LOOP_BRIEF.md` the PI approved before starting (the checkpoint named in the brief (`approve-loop` in the shipped Research paper workflow): the study's sheet → Run overnight, or `arlo approve <slug> approve-loop`; the approval carries the mode); a loop never approves itself.
- **Never stop within budget:** while the brief's budget has room and no stop condition holds, select an action; FULL work behind an unapproved checkpoint waits for the PI (`needs_pi=<checkpoint id>`), and the loop continues with other work.
- **Zero-token monitoring:** while a run is in flight, the only check is `scripts/status.py` on the brief's cadence — no log reading or partial-curve reasoning; each run carries its `budget.max_minutes`, and the Compute panel tracks what the lab spends.
- **Anti-burn backoff:** `loop.no_progress_backoff_cycles` consecutive no-progress cycles → stop with a written diagnosis.
- **`explore` mode** (brief `Mode: explore`): when the plan is exhausted with budget left, the loop expands the frontier and reopens non-headline decisions instead of stopping (capped by `loop.explore_*`); reopening a headline decision / touching the frozen set / exceeding the budget escalates (PI note, or the campaign's bounds + overseer check). `execute` (default) stops at plan exhaustion. See "In-project iteration: execute and explore" above and docs/autonomy.md.
- Every cycle appends a Loop Log row; loop exit does the full session write-back (rule 11) plus a PI morning report.
